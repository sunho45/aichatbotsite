Docker Compose Guide

A practical guide for writing a clean, reliable docker-compose.yaml file for local development and small deployments.

Git Guide JavaScript Guide Nginx Guide Docker Guide Docker Compose Guide

What Docker Compose Does

Docker Compose lets you describe multiple containers in one YAML file, then start, stop, rebuild, and connect them as one project. A typical application might have a web server, API server, database, cache, and background worker.

Compose is best for local development, test environments, demos, and simple single-host deployments. For large multi-server production systems, teams usually move to an orchestrator such as Kubernetes or Docker Swarm.

Recommended File Name

Use compose.yaml or docker-compose.yaml. Modern Docker Compose supports both, but compose.yaml is the current preferred name. This guide uses docker-compose.yaml because many projects still use that convention.

my-project/
  docker-compose.yaml
  .env
  app/
    Dockerfile
  nginx/
    default.conf

Minimal Working Example

This example runs a Node.js API and a PostgreSQL database on the same Compose network.

services:
  api:
    build:
      context: ./app
      dockerfile: Dockerfile
    container_name: myapp-api
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: development
      DATABASE_URL: postgres://app:app_password@db:5432/app_db
    depends_on:
      db:
        condition: service_healthy
    volumes:
      - ./app:/usr/src/app
      - /usr/src/app/node_modules
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    container_name: myapp-db
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app_password
      POSTGRES_DB: app_db
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app_db"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

volumes:
  postgres_data:

Inside Compose, containers reach each other by service name. The API connects to PostgreSQL with host db, not localhost.

Top-Level Sections

Section Purpose
services Defines the containers that make up your app.
volumes Defines named persistent storage managed by Docker.
networks Defines custom networks. Compose creates a default network automatically if you do not specify one.
configs and secrets Advanced sections for configuration files and sensitive values. Support depends on the Docker mode and platform.

Service Fields You Will Use Most

Field Example When to Use It
image nginx:1.27-alpine Run an existing image from a registry.
build context: ./app Build your own image from a Dockerfile.
ports "8080:80" Expose a container port to your computer or server.
environment NODE_ENV: production Pass environment variables into the container.
env_file .env Load many environment variables from a file.
volumes ./src:/app/src Mount source code, config files, or persistent data.
depends_on db: condition: service_healthy Start services in a useful order.
healthcheck pg_isready -U app Tell Compose when a service is actually ready.
restart unless-stopped Restart containers after failures or host reboots.

Correct Port Mapping

Port mappings use HOST:CONTAINER. The left side is the port on your machine. The right side is the port inside the container.

services:
  web:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"

Open http://localhost:8080 on your computer. Docker forwards that traffic to port 80 inside the Nginx container.

Quote port mappings. Without quotes, YAML may parse values with colons in surprising ways.

Environment Variables

There are two different environment-variable moments in Compose:

  • Compose interpolation: Compose reads variables from your shell or a root .env file while parsing docker-compose.yaml.
  • Container environment: Variables listed under environment or env_file are passed into the running container.
# .env
POSTGRES_PASSWORD=change_me
API_PORT=3000
services:
  api:
    build: ./app
    ports:
      - "${API_PORT}:3000"
    environment:
      DATABASE_URL: postgres://app:${POSTGRES_PASSWORD}@db:5432/app_db

Do not commit real passwords, tokens, private keys, or production database URLs. Commit a .env.example file instead.

Volumes: Bind Mounts vs Named Volumes

Type Example Best Use
Bind mount ./app:/usr/src/app Live-edit source code or mount a local config file.
Named volume postgres_data:/var/lib/postgresql/data Persist database files or other generated state.
Anonymous volume /usr/src/app/node_modules Protect container-generated folders from being overwritten by a bind mount. 
services:
  db:
    image: postgres:16-alpine
    volumes:
      - postgres_data:/var/lib/postgresql/data

  postgres_data:

Networks and Service Names

Compose automatically creates a private network for your project. Every service can reach every other service by its service name.

services:
  backend:
    build: ./backend
    environment:
      REDIS_URL: redis://cache:6379

  cache:
    image: redis:7-alpine

The backend uses cache as the hostname because the Redis service is named cache.

Build Settings

Use a short build form when the Dockerfile is named Dockerfile and lives in the build context.

services:
  api:
    build: ./app

Use the long form when you need a custom Dockerfile name, build arguments, or a specific target stage.

services:
  api:
    build:
      context: ./app
      dockerfile: Dockerfile.dev
      target: development
      args:
        NODE_VERSION: "22"

Keep the build context small. Do not use the repository root as the context if the Dockerfile only needs one subdirectory.

depends_on and Health Checks

depends_on controls start order, but start order is not the same as readiness. A database process can start before it is ready to accept connections. Add a health check to the dependency and wait for service_healthy.

services:
  api:
    build: ./app
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app_db"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s

Common Commands

Command What It Does
docker compose up Start services and stream logs.
docker compose up -d Start services in the background.
docker compose up --build Rebuild images before starting services.
docker compose down Stop and remove containers and the default network.
docker compose down -v Also remove named volumes. This deletes database data.
docker compose logs -f api Follow logs for one service.
docker compose exec api sh Open a shell in a running service container.
docker compose config Validate and render the final Compose configuration.

A Production-Oriented Example

This example separates a reverse proxy, API, and database. It avoids live source bind mounts and uses a restart policy.

services:
  proxy:
    image: nginx:1.27-alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      api:
        condition: service_started
    restart: unless-stopped

  api:
    build:
      context: ./app
      dockerfile: Dockerfile
    env_file:
      - .env
    expose:
      - "3000"
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    env_file:
      - .env
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

volumes:
  postgres_data:

Use $$POSTGRES_USER inside the health check when you want the shell inside the container to expand the variable. A single $ is expanded by Compose while parsing the file.

Best Practices

  • Pin image versions, such as postgres:16-alpine, instead of using latest.
  • Use service names as hostnames between containers.
  • Use named volumes for database state.
  • Keep development bind mounts out of production Compose files.
  • Put non-secret defaults in the Compose file and secrets in environment files or a secret manager.
  • Add health checks for databases, queues, and services that other containers depend on.
  • Run docker compose config after editing YAML to catch syntax and interpolation problems.
  • Use .dockerignore so builds do not copy node_modules, logs, Git data, or local artifacts.

Common Mistakes

Mistake Fix
Using localhost from one container to reach another container. Use the Compose service name, such as db, api, or cache.
Storing database files in the container filesystem. Mount a named volume to the database data directory.
Relying only on depends_on without a health check. Add healthcheck and use condition: service_healthy where supported.
Publishing internal services unnecessarily with ports. Use expose or no port setting for services only other containers need.
Committing real .env files. Commit .env.example and keep real secrets out of Git.

Final Checklist

  1. Each service has either image or build.
  2. Only public-facing services use ports.
  3. Stateful services use named volumes.
  4. Services connect using Compose service names.
  5. Secrets are not committed to Git.
  6. Health checks exist for important dependencies.
  7. docker compose config runs successfully.
  8. docker compose up --build starts the full stack cleanly.

If this checklist passes, your docker-compose.yaml is usually in good shape for local development or a simple single-host setup.
